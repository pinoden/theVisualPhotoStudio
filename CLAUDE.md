# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository layout

- **`web/`** is the site: Next.js 16, TypeScript, PostgreSQL. All code lives there. Work happens on the `rebuild` branch and reaches `master` through pull requests.
- **The repository root** holds only this file, a short `README.md` and `.gitignore`.

The site replaced an earlier Flask prototype that lived at the repository root (`app/`, `run.py`, `config.py`, `seed.py`, `migrations/`). It was deleted on 2026-11-15 at the owner's request. Its last version is commit `f1420bc`: list its files with `git ls-tree -r --name-only f1420bc app` and read one with `git show f1420bc:app/templates/faq.html`. It is a reference for page design and copy only. It had unfixed defects: card payments could not succeed, the browser could skip payment, and double booking was possible.

The decisions behind the rebuild, and what is still open, are recorded under "Rebuild decisions" at the end of this file.

## The site (`web/`)

### Commands

Node.js is installed with nvm. A shell that did not load the login profile needs `. ~/.nvm/nvm.sh` first.

```bash
cd web
npm install
npm run dev          # http://localhost:3000 with an embedded database and a pretend card processor
npm test             # every test (vitest)
npx vitest run src/server/bookings.test.ts            # one file
npx vitest run -t "refuses a second booking"          # tests whose name matches
npm run test:e2e     # browser tests (Playwright); starts its own server on port 3211
npx playwright test e2e/a11y.spec.ts                   # the accessibility scan (axe-core) alone
E2E_SHOTS=1 npm run test:e2e                          # also saves full-page pictures to test-results/shots
E2E_NAME=tester E2E_PORT=3213 npm run test:e2e        # a second run at the same time: its own port, database, build and results folders
npx playwright test -g "staff see the day sheet"      # one browser test by name (they build on each other; see below)
npm run typecheck    # generates Next.js route types, then runs tsc
npm run lint
npm run build
npm run check:square # the site's own Square code against Square's sandbox (charges, refunds, a payment link); reads web/.env.square-sandbox; no money moves
npm run db:generate  # after editing src/db/schema.ts: writes a migration into drizzle/
DATABASE_URL=postgres://... npm run db:migrate        # real PostgreSQL only; also adds the website's own pages a database never had
DATABASE_URL=postgres://... npm run db:seed           # real PostgreSQL only
```

Local development needs no database install and no credentials. Without `DATABASE_URL` the app uses PGlite (PostgreSQL compiled to WebAssembly) stored in `web/.data`, migrates it on start and seeds the starting catalog. Delete `web/.data` to reset local data. `web/.env.example` lists the variables for production.

### Architecture

- **Business rules are pure functions in `src/lib/domain/`** (`time.ts`, `pricing.ts`, `availability.ts`). The browser uses them for instant previews and the server uses the same code as the only authority. A new rule about prices or free time belongs there with a test, never in a component or a route.
- **`src/server/`** holds everything that touches the database or the outside world:
  - `catalog.ts` loads studios, opening hours, price rules, add-ons and settings as one serializable `Catalog`.
  - `availability.ts` turns stored holds into per-studio taken time for one day and decides which dates are bookable.
  - `bookings.ts` is the booking service (`createBooking`, `getBookingByToken`).
  - `payments.ts` defines a `PaymentProvider` with a Square implementation (plain HTTPS calls, no SDK) and a mock. A request to Square times out after 10 seconds and is sent again, up to three times; the idempotency key makes a repeat safe. A refused card gets a sentence for the customer from `CARD_PROBLEMS`, and Square's own words go on the payment record. A charge that never gets an answer comes back as `unknown`: the booking is not made, and the customer is told nothing was taken (a booking's card is only reserved, see the booking order). A booking's charge passes `reserve`: Square holds the amount without taking it (`autocomplete: false`) and gives it back by itself after `RESERVE_HOURS` (24) unless `capture` takes it or `release` gives it back first; each of those counts one already done as done. The provider also makes, reads and withdraws a payment link (`createPayLink`, `payLinkState`, `cancelPayLink`: Square's Checkout API). The mock has no payment page of its own, so in test mode the client's page on this site offers a pretend payment.
  - `tz.ts` is the only place that converts between studio wall-clock time (America/New_York) and instants. The browser's one exception is today's date on the studio's clock (`studioToday` in `src/lib/domain/time.ts`, through `Intl`), so a device in another time zone is offered the studio's days. `clockChangeOn` gives the hour the clocks skip or show twice on a day: `loadDayAvailability` counts it as taken in every studio and for the photographer, and `createBooking` and `moveBooking` refuse a time whose real length is not its booked length.
  - `settings.ts` has the default business rules; rows in the `settings` table override them. It also keeps the getting-in text (`loadAccessInstructions`, `saveAccessInstructions`), which is deliberately not part of `Settings`: `Settings` goes to every browser inside the catalog, and that text can hold the code for the building door. The catalog carries only the fact that it is set (`accessInfoSent`).
  - `cached.ts` exposes `getCatalog()` with `'use cache'` and the tag `catalog` for prerendered pages.
- **`src/db/`**: `schema.ts` (Drizzle), `client.ts` (`getDb()` picks PostgreSQL or PGlite; `createMemoryDb()` for tests), `seed.ts` (starting catalog, taken from the studio's live price list).
- **Double booking is prevented by the database.** Every span of time a studio is taken is a row in `studio_holds`, written by bookings and by owner blocks. An exclusion constraint in `drizzle/0001_constraints.sql` rejects two active holds that overlap on one studio. A hold covers the booking plus the studio's clean-up buffer.
- **Booking order in `createBooking`**: validate and price on the server, hold the slot (status `pending_payment`), reserve the amount on the card with the booking id as idempotency key, confirm the booking with the payment recorded as `authorized`, then take the money (`takeReserved` in `src/server/reserved.ts`), which makes the payment `succeeded`. Only `succeeded` payments are money: receipts, refunds and the admin count nothing else. A card is therefore never charged for a booking that was not made: whatever stops before the confirmation, Square gives the reserved amount back. When taking the money does not go through, the booking stands, the payment stays `authorized`, the owner is emailed once, and the scheduled task tries again (`settleReservedPayments`), or gives the amount back if the booking was cancelled first. Taking it locks the booking (`recordTaken`): money taken for a booking that was cancelled while the processor was taking it is given back in full, as a refund that the same run of the task sends. A failed charge releases the slot and gives back any code that was spent. Unpaid holds expire after `holdMinutes`; `releaseExpiredHolds` runs before every availability read and booking attempt, so freeing slots does not depend on the scheduler. After a successful booking the browser loads the booking page as a new document (`navigate` in `BookingFlow`), not through the router, so the finished selection is not kept alive behind it. Each attempt carries a random id (`requestId`) that the screen sends again only when it got no answer at all; the database keeps its SHA-256 (`bookings.request_key`, unique), never the id. A repeat is answered by `answerAgain` before anything is checked again: a booking that was made is answered as the first time, with a second link of its own (`retry_token_hash`; `tokenMatches` takes either), and nothing is booked or charged again; an attempt still on its way gets `in_progress`; one that failed, or that asks for something else, gets `attempt_over`, and the screen starts a new one.
- **Prices** are a table of studio × day type (weekday or weekend) × duration in `price_rules`. Only durations with a price can be booked. `special_dates` reprices a date as the other day type. Booking several studios applies the `multiStudioPercent` setting. The sentence that advertises that discount (`multiStudioOffer` in `src/lib/catalog-view.ts`) asks the pricing function what each number of studios gets, so it cannot promise more than is charged.
- **Add-ons** are taken once per booking (a tick box, never a quantity). Each has a kind (`people`, `pet` or `other`; `src/lib/addon-kinds.ts`) that the owner picks. The guest information and policies pages read the kind, never the name, to say whether larger groups and pets can be booked: through the conditions `pets`, `pet free studios` and `extra people` and the live values `{pet studios}` and `{pet fee}`, which use `petPolicy` (`src/lib/catalog-view.ts`). A booked add-on keeps its kind with the booking (`booking_addons.kind`), like its name and price, because the pet fee has a refund rule of its own.
- **The two booking flows** (studio first, time first) are the same steps in a different order in `src/components/BookingFlow.tsx`. Both read one endpoint, `GET /api/availability?date=`, and compute slots in the browser with the domain functions.
- **Routes**: pages `/` (the home page, a page of the admin drawn by `src/app/page.tsx`), `/book`, `/booking/[ref]?t=<secret>`, `/pay/[id]` (where a payment link leads), `/account` (the client portal: overview, `/account/appointments`, `/account/rewards`, `/account/receipts` and `/account/receipts/[ref]`), `/account/sign-in`, `/staff`, `/admin` (with sub-pages for the calendar, one appointment, bookings, customers and one customer, prices, studios and add-ons, hours, staff, codes, settings, and the website editor: `/admin/website`, `/admin/website/design`, `/admin/website/navigation`, `/admin/website/media`, `/admin/website/media/collections` and `/admin/website/media/collections/[id]`, `/admin/website/fonts`, `/admin/website/pages` and `/admin/website/pages/[id]`), `/dev/outbox`, and any other address, which `src/app/[...slug]` answers with a page of the admin: among them the ones the website was built with, `/studios`, `/rates`, `/policies`, `/faq` (guest information), `/services` (photography sessions) and `/contact`; API `GET /api/availability`, `GET /api/booking-config`, `POST /api/quote`, `POST /api/bookings`, `GET /api/cron/tick`, `GET /account/receipts/[ref]/pdf`, `GET /account/receipts/year/[year]/pdf`, `POST /account/sign-out`, `GET /admin/website/preview`, `POST /admin/website/preview/exit`, `GET /media/[id]/[version]/[name]` (a picture of the media library), `GET /font-files/[id]/[name]` (a file of an uploaded font), `POST /admin/website/media/upload` `POST /admin/website/fonts/upload`, `GET /sitemap.xml` and `GET /robots.txt`. Everything else a signed-in person changes goes through server actions (`actions.ts` next to the pages).
- **Payment mode** is chosen in `resolvePayments`: Square when its three credentials are set; the mock when `PAYMENTS_MODE=mock` or outside production; otherwise bookings that cost money are refused. A booking is never confirmed free because payment is unconfigured.
- **Access control lives in each page and each action**, never in a layout: `requireUser`, `requireStaff` (an attendant, a manager or an owner), `requireManager` (a manager or an owner) and `requireOwner` in `src/server/session.ts`. Someone without the role gets the ordinary not-found page. The admin sidebar (`src/app/admin/frame.tsx`) is rendered by each admin page after its check for the same reason. A role only opens the door: what this person may see and do is asked with `can(viewer, ability, settings)`. The services in `staff.ts`, `manage.ts`, `appointments.ts`, `customers.ts`, `rewards.ts`, `studio-payments.ts` and `pay-links.ts` check the viewer or actor again themselves; the functions in `admin.ts` do not, so every caller must check first (`requireOwner`, or `requireAbility` in `src/app/admin/actions.ts` for the few a manager can be given).
- **`src/server/runtime.ts`** is the glue for requests: site address, which processor and mail service to use, who gets refund notices, and `flushEmailsSoon()` (delivers queued mail after the response).
- **`src/server/auth.ts`** implements passwordless sign-in: emailed six-digit codes, rate-limited to 3 per 15 minutes, hashed in the database. Sessions are 30-day tokens (SHA-256 hashed). `OWNER_EMAILS` controls the owner role; adding or removing an address takes effect at the next request.
- **`src/server/manage.ts`** handles post-booking changes: customer cancellation (with automatic refund by policy), reschedule codes (release the booking and issue a credit), and owner cancel/refund. Refunds are recorded, then sent to the processor with the refund id as idempotency key; failures are retried by the scheduled task. A refund is dated when the processor takes it (`createdAt` is set then): one that goes through when it is tried again belongs to that day, and the booking's history says that it went through, as it says that it failed, or that Square rejected it after accepting it. Only the attempt that turns a refund from waiting to failed writes that line and tells the owner, so two attempts at once (the scheduled task beside a cancellation) tell once; and whether a refund that went through had failed is read as it is marked made, so its history ends with what happened, written after the line that said it failed whatever clock each attempt had; marking a refund failed, its line and the owner's alert are one transaction, so an attempt that goes through meanwhile waits for them. The studio's cancel in the bookings list sends what the card held as the page showed it (`seenCardCents`): money received since (a payment link paid meanwhile) refuses the cancel, for the owner to look again. When the studio cancels, money paid at the studio is named to the owner, in the history and in the client's email, for the studio to give back by hand (`atStudioCents`); the bookings list shows it beside the cancel form (`studioHeldCents`). What can be given back by hand leaves out a pet fee already returned as studio credit that the card did not hold (`studioRefundableCents` in pet-fee.ts), and `recordHandRefund` keeps to it: the pet fee comes back once. A refusal names the part of the pet fee each side held (the credit may have been only part of the fee). A payment record behind a code of studio credit, a pet fee's or a reschedule code's, is not taken back while the code can be spent, nor once any of it was used, whatever became of the booking it paid for (`voidStudioPayment`, `codeStanding` in promos.ts): an owner cancels the code first. What a code was used for is what it was issued for (`promo_codes.issued_cents`, migration 0024) less what is left on it; a pet fee's credit is what its code was issued for (`petFeeReturnedCents`), which is part of the fee when only part was paid, and the appointment page and the bookings list count that part. A booking released for a reschedule code keeps its money on the code: the owner refunds it, to the card or by hand, only up to what is left on the code, whether an owner cancelled the code or not (what was spent of it stays spent), and the refund comes off the code (`rescheduleCodeOf`, `takeOffRescheduleCode` in promos.ts); the bookings list says so beside its refund form, and the client is emailed what is left on the code (`codeRefundEmail`). A processing fee of 100% keeps everything, and the words say so: nothing is asked of the owner. Square accepts most refunds as pending (seen in its sandbox): a refund it has not completed has no `settled_at`, and the scheduled task asks about it again (`checkUnsettledRefunds`, through `refundState`). Completed, it is marked so; rejected after all, it becomes a failed refund: the payment's refunded amount is taken down again, the owner is emailed, and it is retried with the others. A reschedule credit is worth what was paid plus what a percent code took off (`rescheduleOutcome` in `src/lib/domain/policy.ts`). A cancellation gives the booking's code back (`giveCodeBack`): a percent code gets its use back and an amount code from the studio (given by hand, or a pet fee returned) its amount, whoever cancels; a reschedule credit only when the studio cancels before the visit starts. The refund rule (`cancellationOutcome`) keeps two things off the card: the pet fee, which comes back as a code for studio credit, and money taken at the studio, which the owner is emailed to refund by hand.
- **Where a booking's money is** (`src/server/money.ts`): a card charged through the site (`payments.provider` is `square` or `mock`) can be sent back by the site; money taken at the studio and recorded by hand (`provider` `manual`, with a `method` and `recorded_by`) cannot. `netCardPaidCents` counts only the first kind, so every refund the site sends is card money. Every refund recorded counts against what can still be refunded, whatever its state, made, on its way or owed (one that failed is tried again until it is made, or recorded as made in Square): so `netCardPaidCents`, `recordRefunds` and the bookings list, and refunds can never add up to more than was paid. The pet fee stays out of every refund, of card money and of money paid at the studio alike, and comes back as credit (`cancellationOutcome`). `src/server/studio-payments.ts` is "mark as paid": `recordStudioPayment` (all or part of what a booking made in the admin still owes), `voidStudioPayment` (a record made by mistake; it stays, struck out) and `recordHandRefund` (a refund the studio gave by hand). `src/server/pet-fee.ts` is the pet fee: `petFeeCentsOf`, `issuePetCredit` (used by a cancellation in time) and `givePetFeeCredit` (the owner's button when the pet did not come). A fee once returned as credit (`petFeeReturnedCents`) is neither refunded to the card by the owner (`ownerCancelBooking`, `ownerRefund`, and the bookings list's `refundableCents`) nor carried by a reschedule code (`rescheduleOutcome`). Each of them writes a line into the booking's history with the same label on both sides and a note that says what happened.
- **`src/server/pay-links.ts`** is the payment link for what a booking made in the admin still owes. `sendPayLink` has the processor make a link for exactly that amount and emails the client the address of a page on this site, `/pay/<id>`, which leads to the processor's page. Whether a link was paid is asked of the processor (`checkPayLink`): when the client is sent back to that page, when an administrator presses "Check", and from the scheduled task. A paid link becomes an ordinary card payment on the booking (`settle`), so it is refunded like any other. Before a booking is cancelled, by either side, or released for a reschedule code, the processor is asked whether its open link was paid (`noticePaidLink`), so that a payment made just before counts like any other: under the cancellation's terms, or in the code. One that still arrives after the booking ended (the link could not be withdrawn, and was paid later) is recorded and refunded to the card in full at once; the client is emailed (`latePaymentEmail`, put right when that refund does not go through, as a cancellation's email is), and the page the link leads to says it was refunded. A booking has at most one open link (a unique index), no payment can be recorded by hand while one is open, and a booking that stops being active withdraws its link (`closePayLinkOf`). A link is never marked cancelled unless the processor confirmed it can no longer be paid.
- **`src/server/staff.ts`** serves the day sheet: bookings on the days a member of staff may see (their assigned days, or every day with `staffSeesAllDays`), with contact details controlled by `staffSeesContact`.
- **`src/server/appointments.ts`** is one appointment as the admin sees it, for both levels: `getAppointment` (what this viewer may see and do, with the booking's payments and its pet fee), `setLabel`, `moveBooking` (same studios and length, new time; the holds are updated in place, so the database still refuses an overlap) and `createAdminBooking`. `src/server/calendar.ts` loads a span of days for the calendar, and the date maths of its three views is in `src/lib/domain/calendar.ts`. The rules for labels are pure functions in `src/lib/domain/labels.ts`. `src/server/history.ts` writes and reads `booking_events`: call `recordEvent` in the same transaction as any change of a booking's label or status.
- **The admin has three levels** (`src/lib/abilities.ts`). Owners are the addresses in `OWNER_EMAILS` and can do everything. A Studio Manager is the role `manager`, a Studio Attendant the role `staff`. `can(viewer, ability, settings)` answers for all three: an attendant may do what the owners have switched on for attendants (eight switches, the `staff...` settings); a manager can always do what running the calendar needs, and has nine switches of their own (the `manager...` settings: prices, taking payments, refunds, customers, loyalty corrections, blocking time, changing the website's design as a draft, editing its pages as a draft, publishing the website). The owners set both on the Staff page; a change applies at the next request. Prices, studios and add-ons, opening hours, codes, staff and settings have no switch: they stay with the owners. A shared page uses `requireStaff` or `requireManager`, asks the service what the viewer may see, and passes `viewer` and the settings to `AdminFrame`, which builds that person's menu. Someone who may open an appointment and may not see prices gets its history with the amounts taken out (`withoutAmounts`).
- **`src/server/promos.ts`** manages the codes entered at checkout. Three kinds: `percent` (off the studio rental), `amount` (money, decremented as spent: reschedule credits) and `free_hour` (the price of one hour of one studio: the loyalty reward). A code comes from loyalty, from a moved booking, or from the owner, who can make any of the three. Redemption is atomic with the booking. A booking has at most one code.
- **`src/server/tasks.ts`** runs the recurring work: release expired holds, close payments whose result was never recorded (nothing was taken, so nobody is emailed), take the money reserved for bookings that stand and give back what was reserved for ones cancelled first, mark visits complete, send the free hours those visits have earned, retry open refunds, ask the processor about refunds it accepted without completing, ask it about every open payment link (recording the ones that were paid, withdrawing the ones whose booking is no longer active), deliver queued email. Called by `GET /api/cron/tick`.
- **Photography**: a session is an ordinary booking with `photographer_id` set. `createBooking` prices it by its package (`photoPackage` in `quote`), asks `loadDayAvailability` for the photographer's day (`withPhotographer`) and holds the photographer beside the studio. A session needs more notice than a rental: `noticeHours` in `src/lib/domain/availability.ts` (the setting `photoMinLeadHours`, two weeks), used by the server and by the booking screen. `src/server/photography.ts` is the admin side: working hours, blocked time, packages. Wherever a booking stops being active, call `releaseHolds` (`src/server/holds.ts`), which frees its studios and its photographer; do not set `studio_holds.active` by hand.
- **`src/server/loyalty.ts`** counts a customer's stamps and sends the free hours they have earned (`sendEarnedFreeHours`). The rule is a pure function, `loyaltyStanding` in `src/lib/domain/loyalty.ts`: one stamp per day visited, and neither a visit made with a free hour nor a photography session gives one. Visit stamps are never stored: they are counted from the completed bookings, so one visit cannot give two. What an owner adds or takes away by hand is a row of `loyalty_ledger` (who, when, why), counted on top (`stampAdjustmentOf`). What is owed is the number earned less the number ever sent, and each free hour is numbered per customer (`promo_codes.loyalty_seq`, unique with the email), so repeating or racing the task, or correcting stamps, cannot send one twice.
- **The client portal** is `/account` and its three sub-pages, each rendered through `AccountFrame` after its own `requireUser`. `src/server/account.ts` splits a customer's bookings into upcoming and past, filters the past by date, studio and status, and has the words a customer reads for a status (`customerStatus`). `src/server/rewards.ts` lists rewards with a status that is worked out, never stored (Available, Redeemed, Expired, Canceled), and holds the owners' corrections (`adjustStamps`, `cancelReward`, `restoreReward`), each of which needs a reason and writes the ledger. `src/server/receipts.ts` makes receipts from payment records and from nothing else (`loadReceipts`, `yearStatement`); a refund counts on them once it is made, or accepted by the processor ("on its way"), and one owed (failed, or not sent yet) is listed as not made yet and not counted (`ReceiptRefund.state`); a refund is dated when it was sent, and one made by hand in Square when that was recorded: the lines are the prices kept with the booking, never today's price list, and a booking with no payment has no receipt. `src/server/receipt-pdf.ts` draws the same `Receipt` as a PDF file with `@cantoo/pdf-lib`, which is pure JavaScript and needs no file on the server. Everything is found by the signed-in email address, which the sign-in code proved.
- **`src/server/customers.ts`** is the owners' view of customers: `listCustomers` (everyone who booked, searched by name or email) and `getCustomer` (one customer's appointments, receipts, stamps, rewards and codes). A customer is an email address. Both answer null to anyone who is not an owner, staff included, whatever switches are on: a customer's payments are not for staff. The pages are `/admin/customers` and `/admin/customers/[email]`, with the owners' own PDF downloads beside them.
- **The website's content** is what the owners edit under Admin, Website, without a deploy. `src/server/website.ts` is the store: a document (`site_documents`) has a published copy, which the public sees, and a draft, which only the admin sees; `saveDraft`, `publishDraft`, `discardDraft`, `listVersions` and `restoreVersion` are the whole life of one, and every publish keeps a full copy in `site_versions`. Two documents exist so far, each described by a `DocumentSpec` (how to read it, the site as it was built, who may change it): the **design** (`src/lib/site/design.ts`: colours, fonts, text styles, buttons, spacing) and the **frame** around every page (`src/lib/site/frame.ts`: the studio's name and contact details, logo, menu, booking button, footer, social links, announcement bar, the site's title and description). What is stored is never trusted: every read goes through `parseDesign` or `parseFrame`, which give a complete, valid value whatever is in the table, so nothing but a design can reach the stylesheet and nothing but a safe link can become a link. Prices, hours, booking rules and money terms are not documents: they take effect at once, as before.
- **How a page gets that content**: the root layout and the pages call `siteDesign()` and `siteFrame()` (`src/server/site.ts`), never the cached functions directly. They give what is published, from the cache (tag `website`, refreshed by `updateTag(WEBSITE_TAG)` on publish), or the drafts when the request is a preview. A preview is Next.js Draft Mode: `GET /admin/website/preview?to=/path` switches it on for someone who may edit the website, the root layout shows a bar that says so, and `POST /admin/website/preview/exit` or signing out switches it off. The cookie alone is not enough: `isPreview()` also checks that the person is still signed in and still allowed. The editor's phone check narrows a preview to one document with `?website-check=`: a layout cannot read a query, so the proxy (`src/proxy.ts`, which runs for that query only, and whose `config` must hold its name as a literal) hands it on as a header, which `site.ts` reads only in a preview, so that every other page stays as static as it was. The design reaches the browser as CSS variables in a `<style>` element of the root layout (`designCss`); `globals.css` holds the same values as its defaults.
- **The studio's name, address and phone** live in the frame document, and nowhere in the code. Pages read them from `siteFrame()`; what is not a page (an email, a PDF receipt, a form's error message) reads the published ones with `loadBusiness(db)`. Email texts carry the marks `{{studio}}` and `{{address}}`, which `queueEmail` fills in.
- **Fonts**: the library the owners choose from is `FONT_LIBRARY` in `src/lib/site/fonts.ts` (25 fonts). Each is declared for the browser in `src/app/fonts.ts` with `next/font`, under the CSS variable `--font-<id>`, with `preload: false`: a browser fetches a font when a page first uses it. To add one, add it in both files; a test keeps them in step. Beside the library there are the owners' own fonts, uploaded as files (`src/server/fonts.ts`, the tables `site_fonts` and `site_font_files`): a `CustomFont`, whose id in the design is `custom:<uuid>`. A font is added with the owners' own words on the licence they hold. The name a browser gets for it (`uf-...`) is made from its id, and `fontFaceCss` writes the `@font-face` rules for the fonts a design uses, so nothing a person typed reaches the stylesheet. Reading the design needs the list of those fonts, which is why a `DocumentSpec` can have a `context`.
- **Uploaded files** (pictures and fonts) are stored through `FileStore` (`src/server/files.ts`). The one store there is keeps the bytes in the database (`site_files`), because no host has been chosen; a host's own file storage is another `FileStore`, chosen in `fileStore()`. A key names one file for good, so a file never changes once written.
- **The media library** (`src/server/media.ts`, the table `media`) is every picture the website can show. `prepareImage` reads an upload with `sharp` (which is also the check that it is a picture), turns it the way the camera held it, makes it no larger than 2560px, and saves it again in its own format, which leaves behind what the camera wrote into the file. Whatever shows a picture names it by its id and gets a `Picture` from `loadPictures`; its address (`mediaUrl`: `/media/<id>/<version>/<name>`) carries a version that goes up when the file is replaced, so a replaced picture changes everywhere at once. Pages show pictures with `next/image`, which is allowed to resize `/media/**` only (`next.config.ts`). A picture that is shown somewhere cannot be deleted: `mediaUses` looks in the studios' photos and floor plans, the collections and the text of every document, drafts included. The library has no drafts: a change shows at once.
- **Collections** (`src/server/collections.ts`) are named sets of pictures in the owners' order, with an optional first and last day outside which they show nothing (`collectionShows`). **A studio's photos** (`src/server/studio-photos.ts`, the table `studio_photos`) are pictures of the library too; the catalog carries them as `CatalogStudio.photos`, and a picture needs a description before it can be a studio's photo. **A studio's facts** (`src/lib/studio-facts.ts`, the column `studios.facts`) are what photographers choose a studio by: its size, ceiling, light, cyclorama and what comes with it, written under Studios & add-ons, and a floor plan, which is a picture of the library chosen on its own (`setStudioFloorPlan`: owners only, and described first, like a photo). Whatever is stored is read through `parseStudioFacts`. The catalog carries them as `CatalogStudio.facts` and `floorPlan`, and the block "Each studio in full" shows the ones that are written, and nothing where none is.
- **The website's editors** are client components in `src/components/site-editor/`: `useDocumentEditor` (the state: autosave of the draft, one save at a time, each naming the revision it was based on, so a change made elsewhere is noticed; from Publish, Discard or a version brought back until the page the server renders again is shown, the editor is busy and its form `inert`, and what went well is said with that page, in one transition around `router.refresh()`: a change made in between would be thrown away when the editor starts again, or published unchecked; a discard moves the revision on even with no draft stored, so the editor always starts again; while it is busy `change()` takes nothing, no key that changes a page is passed on (Puck's undo and redo, and Delete and Backspace, which delete the chosen block, on the whole document and in its canvas; and in a place that takes typing, any key that types: Enter and Space on a link or a button still work), and the conflict box's buttons wait; before a publish the draft is asked of the server even when nothing changed in this window (`save(false, true)`), so that a draft changed somewhere else is not checked and refused in this editor's name: with nothing changed here the editor shows it at once and says so (that it was changed there, or published or discarded there: the conflict's `waiting`), and with changes here the conflict box asks, naming who saved the draft that waits, or nobody when none waits; and Publish sends the revision that was checked, which the server holds the draft to: `publishDraft` and `publishPage` refuse one changed since, here or in another window, with `DRAFT_CHANGED`), `parts.tsx` (the bar with Save draft, Preview, Publish and Discard; the preview pane, which is the real site in a frame at five screen widths; the history; the form fields), `DesignEditor` and `FrameEditor`. Their server actions (`src/app/admin/website/actions.ts`) answer with a result and never redirect, unlike the admin's forms.
- **Pages made of blocks.** A page made under Admin, Website, Pages is a row of `site_documents` (kind `page`) with the same life as the design: a draft, a published copy, and a copy of every publish in `site_versions`. Its content is `{ meta: { title, description, hidden }, blocks }` (`src/lib/site/page.ts`). The blocks are the site's own: each is described once with `defineBlock` (`src/lib/site/blocks/`), as fields (text, rich, choice, toggle, number, link, picture, pictures, collection, list, slot), and three things follow from that description: the editor's form, a new block's values (`startProps`), and the check of whatever is stored or sent (`parseProps` in `check.ts`, which `parsePage` runs on every block). A field marked `phone: true` has a second value, `<name>Phone`, used below 640px: that is how a page differs on a phone without anything changing on a computer. `registry.ts` lists the blocks by the name pages store, so a block is never renamed. To add a block: describe it, list it, and style it in "Blocks of a page" in `globals.css`. A block placed straight on the page, outside a section, gets the page's width and margins from one rule there (`.blk-root .blk:not(...)`); a block drawn as full-width sections of its own is left out of it.
- **Blocks that show the studio's data, and live values.** The blocks of the group "From the studio's data" (`src/lib/site/blocks/site-data.tsx`: studio cards, each studio in full, the studios' prices, the add-ons' prices, the address, phone and hours, the address and map in a box, the contact form) draw what the admin's other pages hold, from the `catalog` and `business` that `pageSite` (`src/server/pages.ts`) gives every block; only their words are the block's own. The text of a page can name a live value (`src/lib/site/live-values.ts`): `{refund window}`, typed in a heading or in formatted text, shows the setting as it is now ("14 days"). `liveValues` is the list: the studio's name, address and phone, the notice and how far ahead bookings open, the refund window and fee, the rules for moving, the loyalty numbers, photography's notice, refund window and lowest price, the pet fee and its studios, the several-studios offer. `PageBlocks` puts them in after the HTML is cleaned, escaping each one; a name that is not on the list stays as typed, and the editor shows the names, with the list beside the page. A number from the settings that a page should state belongs in `liveValues`, with a test. A link cannot name a live value: a link in text is the text's own.
- **What a page shows only at times** (`src/lib/site/conditions.ts`). A condition is a fact about what the site offers now: pets can come, some studio takes no pets, extra people or any add-on can be booked, a booking can be moved, free hours are on, the getting-in text is written, a photography session can be booked, several studios cost less. Every block has a last field of its own, "Show it" (`when`, added by `defineBlock`), with Always or one condition or its opposite. Words that start with `{if pets}` or `{if not pets}` show only while that holds: a paragraph, list item, heading or quote of formatted text (`showRichText` in `rich-text.ts`, which also drops a list or quote left empty), and a question, card, button or row of a table (the item's title field, in `PageBlocks`). Several markers in a row must all hold. A marker that names no condition is no marker and stays visible. The editor shows everything and marks a block whose "Show it" is set; Preview shows the page as visitors see it now. A new switch that a page should follow belongs in `CONDITIONS`, with a test. What conditions do not cover, a number set to 0, is the owners' to word.
- **The pages the website was built with** (`src/lib/site/built-in-pages.ts`): the home page and the six public pages that were written in code until 2026-11-16, as blocks with the wording they had, live values for every number and conditions where the code had an `if`. `ensureBuiltInPages` (`pages.ts`) puts each into a database once, published, with version 1 by "the site as it was built", and marks it with `site_documents.built_in`: run when PGlite opens (`getDb`) and by `npm run db:migrate`, never in the unit tests' `createTestWorld`. A page a database had once is never put back, whatever the owners did to it, so a deleted one waits in the trash for good (`emptyOldTrash` leaves it). Its history can "Start again from the page as it was built" (`restorePageVersion` with `BUILT_VERSION`). The home page is the page whose address is "": it cannot move, be taken offline or be deleted, and a copy of it goes to `/home-copy`. Changing the starting content changes nothing in a database that has the page already: it is only where a new database starts.
- **Formatted text** is HTML, cleaned by `sanitizeRichText` (`src/lib/site/rich-text.ts`, with `sanitize-html`) when a page is saved and again when it is drawn. It keeps paragraphs, bold, italic, underline, links (through `parseHref`), lists, h2 to h4, quotes and alignment, and nothing else. It never parses a style: a paragraph's or heading's `style` is written anew from its alignment alone (`aligned`, with `parseStyleAttributes: false`), because sanitize-html's style parsing runs postcss, which draws random numbers, and Next.js refuses `Math.random()` while it prerenders a page (the home page is prerendered). The cleaner is for the server only: `fields.ts`, the block files and `paragraphs.ts` go to the browser with the editor; `check.ts` and `rich-text.ts` must never be imported by anything a client component imports.
- **`src/server/pages.ts`** is the page store. `createPage` makes a draft, at an address made from the name unless one is typed; `duplicatePage` copies a page as a draft; `savePageDraft` has the design's revision check; `publishPage` is refused while a picture on the page has no description; `unpublishPage` keeps the page as a draft; `discardPageDraft`, `listPageVersions` and `restorePageVersion` work as for the design. `savePageSettings` changes the name and address at once; moving a published page writes a redirect from the old address and points earlier ones on. `deletePage` puts a page in the trash, `restorePage` brings it back as a draft, and `emptyOldTrash`, run by the scheduled task, removes it after `TRASH_DAYS`, unless the website was built with it. Old addresses are `site_redirects` (`findRedirect`, `addRedirect`, `removeRedirect`); `addRedirect` refuses one that would lead back to itself, by its path (the public route does not look at what follows ? or #, and the website takes off a slash at the end; a full address of the site itself counts as its path: any of the addresses it is known by, `siteOrigins` in runtime.ts, which are `SITE_URL` and the one the request came in at, with "www." or without, with a dot at the end or without, and with every name of the computer itself as one) or round through other old addresses (`roundBack`), where only a published page stops the round; paths are compared as a browser reads them ("." and ".." resolved, also written %2e, escapes decoded). A draft page moved onto an old address leaves it leading on until the page is published, unless it leads round to the page itself, and then it is dropped; what led to the page's old address follows it to the new, however it was written, and with its #section or ?query. Publishing a page drops an old address that led away from its own, so taking the page off later cannot start a round. `linksToPage` says, in words, what links to a page (`frameLinksTo` in `frame.ts`, `pageLinksTo` in `page.ts`), for the warning before a page leaves the website. Editing needs `editPages`; whatever changes what visitors see needs `publishWebsite` as well.
- **The public route for pages** is `src/app/[...slug]/page.tsx`. Next.js tries every other route first, so it only gets addresses the site has no route for. It shows the published page (`getPublishedPage`, cached with the tags `website` and `catalog`), or in a preview its draft (`sitePage` in `site.ts`). Otherwise an old address answers 308 (`getRedirect`) and anything else 404. A sample in `generateStaticParams` and `export const instant = false` are what let it answer with those status codes. A page is drawn by `PageBlocks` (`src/components/site/PageBlocks.tsx`), a server component that gives each block its values: formatted text as the cleaned HTML, a place for blocks as the drawing of its blocks. The home page has its own route, `src/app/page.tsx`, which draws the page at "" the same way. The addresses a page cannot take are `RESERVED_SEGMENTS` in `page.ts`: the site's own routes; a new route of the site's own needs its first part there too. `src/app/sitemap.ts` lists the published pages that are not hidden, the home page among them, and the booking steps; `src/app/robots.ts` keeps search engines out of the admin, the accounts and the private pages.
- **The page editor** is Puck 0.24.0 (`@puckeditor/core`, pinned exactly), loaded in the browser only (`PageEditorLoader`, with `ssr: false`). `buildPuckConfig` (`src/components/site-editor/puck-config.tsx`) makes Puck's configuration from the blocks, with the site's own fields for links, pictures and galleries (they open `PictureChooser`); `toPuckData` and `fromPuckData` turn the site's page into Puck's data and back without a change. `PageEditor` puts the site's bar above Puck (`useDraftEditor`: the autosave and conflict check of the design's editors) and gives Puck's frame the site's fonts. On a wide screen the page editor's admin page folds the admin's menu away (`AdminFrame` with `wide`).
- **The page editor's guard rails** (requirement 24). Before a page is published, the editor draws its draft as visitors would get it (`/admin/website/pages/[id]/check`, for whoever may edit it) in a frame 320px and then 390px wide, transparent and behind the editor, waits until the page is on screen with the site's stylesheet (it arrives in parts, shown by a script after the frame loads; a frame out of sight or hidden may never be drawn), and measures it with the phone tests' own checks (`src/lib/site/phone-checks.ts`: nothing wider than the screen, controls at least 40px tall, fields with 16px text, no text under 11px). A page with a problem is not published, and the editor says at which width and what, by its own words ("BOOK A STUDIO" reaches 336px) (`checkOnPhones` in `src/components/site-editor/phone-check.ts`, run by `useDraftEditor` through `DraftActions.check`). It is a guard against mistakes in the browser, not a lock: the server publishes what an editor sends. A change of the design, or of the header, menu and footer, reaches every page: before it is published, every published page (hidden ones included: they are public at their address), the two booking screens and the account are drawn as they will be once that one change is published (`checkWebsiteOnPhones`, with the list the server gives at the moment of publishing, `checkPathsAction` and `websiteCheckPaths`, so that a page published meanwhile is among them): at 320px, the home page and the booking page at 390px as well, three at a time. A page counts as drawn once its header is fixed by the stylesheet, every part the server streams is shown (React marks a part still to come with the comment `$?`, and with `$~` while it waits to be shown: `partStillComing`), and no `.spinner` stands where a part is still to come in the browser; a page with nothing on it is drawn, for it fits any phone. One that does not arrive in time is asked for once more, and a refusal names it. A problem found on many pages names a few and counts the rest, or says "every page" (`pagesListed`). A page with a problem is measured again as visitors have it now (`?website-check=published`): when it has no more problems of each kind than before and none of them worse (reaching further, or smaller to read or to touch; each sentence is read by how it ends, `SENTENCES`, so the words of the element it names, capitals and numbers included, do not count), they are not the change's doing (`broughtBy`), and "Published" names them as visitors have them once the change is out (`already`); a new kind of problem, or a wider page, refuses the change. The page editor's own check does the same for a page on the website, with its route's `?as=published`, so that a problem the studio's data makes on a page (a long word in an add-on) does not keep the page's own changes back. Each is asked for with `?website-check=design` or `frame`, which shows that document's draft and everything else as published, whatever other drafts wait; a page's own check asks with `page`, so the design and the header are as published there too (src/lib/site/website-check.ts).

What the Reviews block shows is not given to search engines as review markup: they do not count the reviews a business shows of itself. In production `SITE_URL` must be set, or the sharing card has no picture address and the JSON-LD no address of the website.

A message can carry a reply address (`reply_to`).

### Conventions and gotchas

- **Next.js 16 differs from older versions.** Read the bundled guide in `web/node_modules/next/dist/docs/` before using an API you have not verified there (`web/AGENTS.md` says the same).
- **Cache Components is on.** A page that reads uncached data must put it behind `<Suspense>` or cache it with `'use cache'`. A page rendered per request (see `src/app/booking/[ref]/page.tsx`) calls `await connection()` first. Never cache bookings or availability.
- **The linter rejects `setState` called synchronously in an effect.** Derive values during render, or set state from event handlers and promise callbacks.
- **Money is integer cents. Times in the database are `timestamptz`.** Domain functions work with a `YYYY-MM-DD` date and minutes from local midnight.
- **Never trust totals from the browser.** `POST /api/bookings` recomputes the price and compares it with `expectedTotalCents`, so a customer is never charged an amount they did not see.
- **Text from a form goes through `formText`** (`src/lib/parse.ts`) before it is measured or stored. A browser sends a line break as two characters while a field's `maxlength` counts it as one; without this, text the field accepted is refused as too long. It also drops the NUL character, which PostgreSQL refuses.
- **Amounts the owner types go through `dollarsToCents`.** It takes a comma only between thousands: "12,50" is refused, not read as $1,250. Money fields spread `MONEY_FIELD`, so the browser applies the same pattern before the form is sent.
- **An admin form the server refuses comes back with the stored values, not with what was typed.** The browser's own checks (`required`, `type="number"` with a range, `maxLength`, the money pattern) are what keeps typed text from being lost, so give every new field the check that matches the server's: `EMAIL_FIELD`, `MONEY_FIELD`, `PRICE_FIELD` (up to $100,000) and `CREDIT_FIELD` (above zero) in `src/lib/parse.ts`. There is one rule for an email address, `EMAIL_RULE` (the booking's own `z.email()`): sign-in (`normalizeEmail`), bookings, the admin's forms and the fields' pattern follow it, and a test keeps them in step. The booking screen, sign-in and the contact form follow it too, and the booking's own refusals name a field in the screen's words (`FIELD_WORDS` in bookings.ts). A number field lets through what `intInRange` reads ("5.0", "1e3", ".5e2", "0050"). Text that must say something (a picture's description, a review) is checked with `hasVisibleText` (`src/lib/visible-text.ts`), which counts neither spaces nor characters that show nothing. The settings' ranges are `NUMBER_SETTING_RANGES` (`src/server/settings.ts`), which the Settings form reads for its `min` and `max`; their words are in `src/app/admin/settings/fields.ts`.
- **A sentence with a number the owner can change** uses `count` and `hoursInWords` from `src/lib/words.ts` ("1 day", "100 hours", "7 days"), and has to read well when the number is 0 or 1.
- **A code's issue date is the moment of the change that issued it** (`issuedAt` in `issuePromo`), not the database's clock: a reward shows the day it was earned.
- **A PDF knows Western European letters only.** The receipt files use the fonts every PDF reader has built in. `pdfSafe` writes any other letter as its plain letter or as "?", so a name in another alphabet cannot break a download; the screen shows it in full.
- **Constraints written by hand are not in `schema.ts`.** Add new ones with `npx drizzle-kit generate --custom --name <name>`.
- **Try a new migration on a copy of the local database before committing it.** Stop the development server, copy `web/.data/pglite` somewhere else, open the copy with PGlite and its `btree_gist` extension, run Drizzle's `migrate` with `web/drizzle`, and look at what it left. Migrations 0011 to 0023 were tried this way.
- **PGlite's data folder can be opened by one process at a time.** Stop `npm run dev` before running anything else against `web/.data`. `next build` without `DATABASE_URL` prerenders from an in-memory copy of the starting catalog.
- **Tests** come in four kinds: domain unit tests; server tests against an in-memory PGlite, set up by `src/server/testing.ts` (the real constraints are exercised); component tests of the booking screen in jsdom; and browser tests in `web/e2e/`. The pretend processor has a card whose every refund is refused (`MOCK_TOKEN_REFUNDS_REFUSED`), which a browser test sends in place of the usual one, so that a refund that fails can be tried in a browser. Resend has never been called. Square has been called in its sandbox only, by `npm run check:square`, which is not part of `npm test`.
- **The accessibility tests** (`e2e/a11y.spec.ts`) scan the public pages, every step of a booking, a customer's account and the pages of the admin with axe-core, against WCAG 2.1 A and AA. They run first, on an empty database: the pages that need a booking, a customer or a page are scanned in the other test files, where those exist, with `accessibilityProblems` (`e2e/helpers.ts`, whose `exclude` leaves out what is not the site's own). Colour contrast is left out: the brand's colours are the owners' choice. A new page or control has to pass them: a link inside a sentence is underlined (the rule after the base link style in `globals.css`), and a control named with `aria-label` has its visible words in that name.
- **The mobile tests** (`e2e/z-mobile.spec.ts`) measure with the functions of `src/lib/site/phone-checks.ts`, which the page editor runs too: each must stay complete in itself, because Playwright sends it into the page as text. They run after `site.spec.ts`, on the database it leaves, with the fourth owner address (`owner4@studio.test`) and their own customer and days. A new page or control has to pass them: nothing wider than the screen (only a box made to scroll sideways excuses what is wider: `.data-table-wrap`, `.blk-table-wrap`, or one marked `data-scrolls-sideways`; the admin's column, which scrolls up and down and so sideways too by the rules of CSS, does not, so a wide table on an admin page goes in a `.data-table-wrap`, and the admin's buttons, which often carry a name the owners typed, wrap it: `.admin-main .btn`), controls at least 40px tall, fields with 16px text, and no word broken in two that would have fitted on its line (`brokenWords`, which the page editor does not run yet; a word in a box of a flex or grid row, a button among buttons, could have had the row's width less that box's own padding). A row of two sides, a label and its price, never squeezes either: in `.price-row` the first side may be as narrow as its longest word (`flex-basis: min-content`), and the second moves to a line of its own only when a word would otherwise break; an add-on row has its name and price on one such line (`.addon-head`) and its description below, so a word is broken only when it is longer than a whole line, as a web address in a description is. The phone tests measure the booking screens, the booking page, the account and /rates with an add-on of such words, which they add (`LONG_ADDON`). The rules that make this so are the last blocks of `globals.css` ("Phones").
- **Browser tests** start their own dev server on port 3211 with a throwaway database (`.data/e2e`), their own build folder (`.next-e2e`), `SITE_URL` set to their own address, the mock processor and eleven owners (`owner@studio.test` to `owner11@studio.test`). Sign-in codes are limited to three per address in 15 minutes, and the first three owners each use all three in `site.spec.ts`; the fourth is for the mobile tests, the fifth for the customers test, the sixth to tenth for `website.spec.ts`, and the eleventh for `a11y.spec.ts`. In the page editor a block is dragged with `dragBlock` (`website.spec.ts`), which puts it in the middle of the list of blocks (giving the list room below its last block, so that it too can be put there) (a drag that starts at the list's edge makes the editor scroll by itself, and the drop lands elsewhere) and moves the mouse in steps; those tests use a window 1200px high, so that the editor is on screen. The editor draws the page zoomed out, which Playwright's `boundingBox` does not count: a drop at the bottom of a block (the default) lands on the page's top level, after everything; to drop into an empty place for blocks, such as a column, use `"middle"`, which aims through the zoom (`onCanvas`). Change Puck's fields one at a time, waiting for each to show on the page: two changes made at once can lose the second. An item of a list in Puck's panel (a review, a card) opens when its summary is pressed (`[class*="ArrayFieldItem-summary"]`, "New" while its title is empty). Puck keeps a copy of the panel out of sight, so a locator that is not a role locator needs `onScreen`, or the click waits for the hidden copy until the test times out. The files run in the order of their names: `a11y.spec.ts`, `site.spec.ts`, `website.spec.ts`, `z-mobile.spec.ts`. `website.spec.ts` changes the design and the menu and must end with them as the site was built, because the phone tests after it measure the site's own design. The two photos, the facts and the floor plan it gives Studio Blanche stay, so the phone tests also measure a studio that has all of them. `accessibilityProblems` (`e2e/helpers.ts`) is the accessibility scan's check, for a test that wants to scan a page it changed. It waits for the page's title first: after a form is sent, the framework puts the title back a moment after the page, and a scan in between reports a page without one. Its pictures are made in the test with `sharp`; its font files are two real ones that come with Next.js, read from `node_modules`. When a new test needs an owner and they have run out, add another in `playwright.config.ts`. The suite books from one address more than ten times a minute, so its server raises the booking limit with `BOOKING_REQUESTS_PER_MINUTE` (ignored in production); without it the last tests fail with "Too many requests". They read sign-in codes from `/dev/outbox`. They share one database and run in order, so a single test run with `-g` only works if it does not depend on an earlier one. Any error in the browser console fails the test. A second run can go on at the same time under its own name: `E2E_NAME=tester E2E_PORT=3213` gives it `.data/e2e-tester`, `.next-e2e-tester` and `test-results-tester`. `tsconfig.json` already lists the `tester` build folder; with another name Next.js would add lines there on its first start.
- **Earlier pages stay in the document, hidden.** With Cache Components, the router keeps recently visited pages mounted (`display: none`) so their state survives going back. Client state therefore outlives navigation: reset it deliberately where that matters. Signing out is for the same reason a plain form post to `/account/sign-out` and not a server action: the browser loads a new document, so nothing of the pages a signed-in person had open stays behind. In browser tests use role locators, or `byLabel`, `byText` and `onScreen` from `e2e/helpers.ts`; a plain text or label locator also matches the hidden copies.
- **After a route is deleted, remove its generated types.** `web/.next/dev/types` and `web/.next-e2e/dev/types` still name the deleted page, and `tsc` fails on them. With no server running, delete those two folders; `npm run typecheck` writes the types again.
- **One build folder, one process.** A dev server started on a build folder that another process is still writing to corrupts the cache, and every page then reloads in a loop (about 30 times a second, with nothing in the log but "Compiled"). It happened twice: with two sessions active, and when a server was started within a second of killing the previous one. Wait for the old process to exit before starting a new one. To recover, stop the servers and delete `web/.next/dev`. The browser tests avoid it by building into their own folder, `.next-e2e` (`NEXT_DIST_DIR`), which they delete at every start.
- **More than one Claude Code session may be working in this checkout.** Before committing, run `git status` and `git log -5`, and commit only what you changed and verified.
- **A button whose `formAction` is a server action cannot have a `name`.** React overrides it and logs an error, which fails the browser tests. Give each button its own action (see the two add-on actions in `src/app/admin/actions.ts`).
- **One stylesheet.** `src/app/globals.css` was carried over from the Flask prototype. Its first `:root` block is the design: the same values as `DEFAULT_DESIGN`, which a test compares, so change both together.
- **Text styles are for the public pages only.** A public page wraps its content in `.site-page`; inside it running text and headings follow the design's sizes, weights and spacing. The booking steps, the account and the admin are outside it and keep the sizes they were tested with; they follow the design's colours, fonts and buttons only. A heading's size on a public page is the size its place gives it times the design's scale, so a rule (or an inline style) for such a heading sets `--h1-base`, `--h2-base`, `--h3-base` or `--h4-base`, never `font-size`.
- **Text on the accent colour is `var(--on-accent)`,** never `#fff`: the owners can make the accent light.
- **The header folds its menu by itself.** At 1000px and less the stylesheet does it; on a wider screen `SiteNav` measures whether the logo and the links fit and sets `data-folded`. The folded rules exist twice in `globals.css` for those two cases (and twice more under "Phones"): change them together.
- **A draft-mode preview needs HTTPS in production.** Next.js sets its cookie `Secure` there. On `localhost` in development it works over HTTP.
- **Never change an element of a page from outside React,** a page shown in a frame included: do it before the page has started and React reports a mismatch with the server's HTML, which fails the browser tests. To restyle a framed page, give its document a stylesheet of its own (`adoptedStyleSheets`, see `overlayCss` in `parts.tsx`).
- **Forms do not nest.** The page editor's panel is Puck's own form, and the fields the site adds to it (links, pictures, the picture chooser) are inside it: they use no `<form>`, and every button in them is `type="button"`.
- **A field's `pattern` is read with the `v` flag** by today's browsers: inside `[...]`, escape `/` and `-` (`[A-Za-z0-9\/\-]`). Otherwise the browser logs an error, which fails the browser tests.
- **The page editor (Puck), as its code shows it** (its documentation leaves these out): it cleans nothing it is given, which is why the site has its own cleaner and its own renderer for visitors. At run time it injects a stylesheet that loads a font from another server unless its CSS is already on the page; `no-external.css`, imported by `PageEditor`, is that CSS without the font. `<Puck>` reads `data` only when it mounts, so the editor gets a new `key` after a publish, a discard or a version brought back. Its canvas is a frame that takes the admin page's stylesheets (`syncHostStyles`) but not the classes on `<html>`, so `PageEditor` gives the frame the font classes. A custom field's `render` gets `{ field, name, id, value, onChange, readOnly }`; a slot is drawn as `<Content className="…" />`. Check these again before upgrading it.
- **A file goes to a route handler, never to a server action.** A server action refuses a request over 1 MB. The two upload addresses check the size before reading the file, and answer in JSON (pictures, sent by the uploader one at a time) or by sending the browser back with a message (fonts, a plain form). In a route handler cached pages are refreshed with `revalidateTag(tag, { expire: 0 })`: `updateTag` works in server actions only.
- **A control that only the page's code in the browser can work is disabled until the page has started** (`useStarted`, `src/components/use-started.ts`). A file chosen in the media library's "Add pictures" or "Replace the file" before then was lost without a word. The design and the header editors' fields wait too (their form is a `<fieldset disabled>` until then): what a second window typed at once never reached the editor. A browser test waits for such a control to be enabled before it uses it.
- **A `page.tsx` may export only what Next.js expects of a page** (the page, `metadata`, `generateMetadata`, `generateStaticParams`). A helper that another file needs goes in a module of its own, or the build fails.
- **`sharp` is a native module.** It is installed for the machine it runs on; `npm install` on the host fetches the right one.
- **A browser-test run started in the background** must end with the test runner's own exit status. `npx playwright test > log; echo done` reports success whatever the tests did: read the log's last lines before saying a run passed.
- Next.js telemetry was turned off on this machine with `npx next telemetry disable`.

### Known gaps in what is built

Not connected to the outside world yet:

- **Square is verified in its sandbox only.** Through the site's own code: a charge, the same charge sent twice, four kinds of refused card, partial and full refunds, a refund read back while pending, an amount reserved then taken (and taking it twice), an amount reserved then given back (and giving it back twice), and a declined card refused when reserving (2026-11-16: Square accepted it as PENDING); a payment link made, asked for twice, read while unpaid, withdrawn, and read once paid. In a browser: Square's card form, a refused card, a paid booking and its refund; and the sandbox's test page for a payment link, where a link was paid and its payment then refunded. Never done: a payment with production keys, and Square's real payment page for a link, which the sandbox replaces with a test page. The browser tests still use the pretend processor, so the card form is checked by hand, not by a test that runs every time.
- **No email has ever been sent.** The Resend transport is written but untried. In production, without `RESEND_API_KEY` and `EMAIL_FROM`, nothing goes out, including sign-in codes, so nobody could sign in.
- The owner will choose the email service later (answer 2, 2026-11-15).
- **Nothing calls the scheduled tasks.** `GET /api/cron/tick` must be called every few minutes by a scheduler (with `CRON_SECRET`). Until then visits are not marked completed, no free hours go out, and failed refunds are not retried. A payment link that was paid is still recorded without it, when the client is brought back to their page or an administrator presses "Check whether it was paid"; a client who closes Square's page before being brought back is noticed only by the scheduled task.
- The owner chose the hosting service's own scheduler for these tasks, once a host is chosen (answer 4, 2026-11-15).
- **No production database, hosting or domain** has been chosen. The owner will decide the hosting later (answer 1, 2026-11-15).
- **The client portal has no history from before this site.** Earlier appointments and payments from the live site (Acuity and Square) are not imported. Sign-in is still the emailed code only: no password, no Google.
- An owner cannot change the email address a customer's records are kept under, or join two addresses of one person: both wait for the owner's answer (requirement 19). Nothing records which owner opened which customer's page; corrections are recorded.
- Receipts show no tax line, and the yearly PDF is a summary of payments, not a tax document: the accountant's rule is still needed. There is no privacy policy page yet.

Known weaknesses:

- Conditions follow the switches of the site (pets, moving, photography, free hours, getting in, several studios, add-ons). A number set to 0 is not one of them: with a refund fee of 0 the policies would say "(0%)", and the owners reword the sentence.
- A link cannot name a live value. The guest information's "Open in Maps" link and the studios page's "7457 Aloma Ave" are text: if the studio moves, change them with the header and footer.
- A page the website was built with and then deleted waits in the trash for good, so that it does not come back by itself.
- Puck is pinned at 0.24.0, and the site relies on facts read from its code (see "The page editor (Puck)" under Conventions): check them again before upgrading it.
- The page editor's undo history is Puck's, and is lost when the page is opened again.
- The trash of pages is emptied by the scheduled task, which nothing calls yet: until something does, deleted pages stay in the trash.
- All 25 fonts of the library are declared in every page's stylesheet (about 5 KB more to download, compressed), and no font is preloaded, because which fonts are in use is only known when a page is served. A visitor's first page therefore shows its text in a fallback font for a moment.
- An announcement with dates appears and goes within a few minutes of midnight on the studio's clock, not on the second: the published frame is cached and worked out again every few minutes.
- A preview belongs to the browser. Until "Leave the preview", signing out or closing the browser, that browser sees the drafts on the public pages too, under the bar that says so.
- The readability list compares six pairs of the design's colours. It knows nothing about words placed over a photograph.
- Two people in one editor are noticed when the second saves. Nothing shows that someone else has it open.
- An announcement a visitor closed shows again for an instant each time a page is loaded as a new document, until the page has started. Moving between pages inside the site does not show it.

- A full address of the site under a name the host also gives it, which is neither `SITE_URL` nor the address the owner is using when they add it, is not known for the site's own: an old address could lead to it and send visitors round.
- A cancellation's email that has already left when its card refund fails is followed by a second email that puts it right; the first still said the refund was on its way.
- When the page the editor is drawn again with after a publish does not arrive (the connection drops, or the server answers with an error), Next.js loads the page anew and "Published" is not said: the editor's status line then says that there is nothing to publish.
- A word broken in two is checked by the phone tests, not yet by the page editor's guard rails.
- The contact form has no CAPTCHA. A hidden field that only programs fill in, and the limit of 5 messages in 10 minutes, are its only protection against automated spam.
- `POST /api/bookings` is rate-limited to 10 requests a minute per address, in memory. The contact form's limit works the same way. That is per server process, keyed by the `x-forwarded-for` header (everyone shares one bucket when it is missing), and nothing else is limited by address.
- A booking whose reserved money could not be taken stands unpaid until the scheduled task takes it, and nothing calls that task yet: after 24 hours Square gives the amount back and the owner, who was emailed, collects the payment at the studio or cancels the booking. A booking cancelled while its money was only reserved gives it back in full, whatever the cancellation terms say.
- A refund Square rejects after accepting it is noticed by the scheduled task, which nothing calls yet. When a failed refund is retried, Square answers with the same rejected refund, because the refund's id is its idempotency key: the owner refunds such a payment by hand in Square, and records it on the admin's overview ("Refunded it in Square", `recordRefundMadeInSquare` in manage.ts, for a refund that failed only): the site then counts it as made and stops trying.
- The getting-in text reaches anyone who books. A booking made far ahead and cancelled in time costs only the 5% fee, and nothing when the fee is 0. Sending the text shortly before the visit, not at booking, would close this; the live site sends it at booking.
- An admin form the server refuses comes back with the stored values. The browser's checks stop the usual causes first (see "Conventions and gotchas"). Only the contact form hands typed values back.
- Two add-ons can have the same name (a pet fee for each of two studios). A booking with both lists the name twice, at two prices.
- The development build sometimes reports a script error of React's own performance timeline when a signed-in customer or staff member opens an owner page ("Failed to execute 'measure' on 'Performance': '... [Prerender]' cannot have a negative time stamp"): the tester saw it on 2026-11-15, and it failed the staff test once on 2026-11-16. It is not the site's code, and a production build has no such timeline, so the browser tests leave this one message out (`frameworkNoise` in e2e/helpers.ts); any other error still fails a test.
- The development server once logged "Worker terminated due to reaching memory limit: JS heap out of memory" during the tester's hour-long session, and kept answering. Cause unknown.
- A visit counts towards a free hour once it is completed. If staff mark it a no-show later than `loyaltyDelayHours` after it ended, a free hour it helped to earn has already been sent. The owner can cancel that code in `/admin/codes`; no second hour is sent for the same visits.
- The owner can edit each studio's tagline, description, guest number and clean-up time, and the add-ons, under "Studios & add-ons" (2026-11-15). A studio's photos are chosen there too, from the media library (2026-11-15), and its facts and floor plan are written there (2026-11-16). Not yet from the admin: a studio's name, and adding or removing a studio; those are database rows. The Flask prototype's admin had a calendar, reports, a customer list, announcements and an iCal feed; none of them were carried over.
- A payment taken at the studio can be recorded only up to what the booking owes. Money taken for something else (overtime, the cleaning fee, damage) has nowhere to be recorded.
- Returning a pet fee as credit is the owners' alone: there is no switch that lets staff do it.
- Square refuses to make a payment link when it does not like the buyer's email address (in the sandbox it refused an example.com address), so the site does not send Square the client's email with a link. The site learns that a link was paid by asking Square, not by being told (no webhook is set up). Square's documentation does not say whether a link expires by itself; an open link stays open here until it is paid or cancelled.
- An administrator's move keeps the price that was paid, also when the new day is priced differently (a weekday moved to a weekend).
- There is one photographer, and no page to add a second or to rename them: that is a row of the `photographers` table. The site books the first active one.
- A studio shows a tinted box until the owners give it photos (Studios & add-ons). No real photograph has been uploaded yet: the tests use pictures of one colour.
- Uploaded pictures and fonts are kept in the database. That works anywhere and needs nothing set up, and it is not where a few hundred photographs should stay: a host's own file storage should take them over (`fileStore()` in `src/server/files.ts`).
- A photograph in Apple's HEIC format cannot be read: it is refused with a sentence that says which formats can. An iPhone sends JPEG to a web page by itself unless it is told otherwise.
- Where a picture is used is found by looking for its id in the text of every document, which is right as long as the documents are few and small.
- The framework keeps the resized copies of a picture for as long as the picture's address is valid, and there is no way to clear them. A replaced picture gets a new address, so this never shows an old picture; the old copies only take room until the host clears its cache.
- The browser tests run against the development server with the mock processor, not a production build.
- Mobile was checked in Chromium set to phone sizes. Safari on an iPhone lays some things out differently (date and time fields above all), and nothing was tried on a real phone, a real foldable or with a screen reader.
- The accessibility scan leaves out colour contrast and Puck's own canvas in the page editor. Since 2026-11-16 the pages that need something chosen first (a booking, an appointment, a customer, a receipt, a payment link, a collection, the page editor around the canvas) are scanned where the other tests make them, with something in them. Nothing was tried with a real screen reader. The tan accent falls short of the contrast WCAG asks for as the colour of links and under white words on a button; changing it is the owners' choice.
